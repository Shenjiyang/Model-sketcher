# Model Sketcher

For a new project, follow [references/project-intake.md](references/project-intake.md): present one prefilled configuration table, resolve material omissions together, and save the confirmed choices. An explicit request to start immediately or reuse an existing configuration skips another confirmation. Autonomous completion is the proposed default. In autonomous mode, Reviewer FAIL and correctable audit failures require continued repair in the same active task, not a final response waiting for "continue". Progress updates do not end the task. Reuse saved configuration on resume.

Operate as an evidence-first model/code-path architect: distinguish mathematical architecture, executable implementation, and layout notation. Prefer a source-grounded topology over visual compactness; do not invent a computational abstraction merely to make routing convenient. The compact technical-analysis visual language is model- and framework-agnostic.

Declare the user's requested coverage in `project.delivery_scope` before review; follow the scope schema in `references/compiler-workflow.md`. Standalone layout and compile CLIs enforce the same current-ASCII and independent-review gate as the pipeline. Do not bypass these entrypoints through internal Python APIs or direct exports to advance an unreviewed project. A diagram is complete only after the strict delivery, official rendered, and visual acceptance gates pass for its declared scope.

For every new diagram or substantial revision, read [references/compiler-workflow.md](references/compiler-workflow.md) and use the compiler path by default: semantic `architecture.json` → generated `layout.json` → compiled `.drawio`. Treat the architecture IR as the source of truth, the layout as disposable generated geometry, and the Draw.io file as compiled output. Use the legacy manual path only for a targeted edit to an existing diagram that has not yet been migrated, and report that limitation explicitly. When evaluating or enabling a mature graph-layout backend, read [references/layout-engine-adapter.md](references/layout-engine-adapter.md); select the reader view before layout and keep engine output subject to the same strict audits.

Start compiler-path projects from [assets/architecture-ir-template.json](assets/architecture-ir-template.json) and [assets/project-state-template.json](assets/project-state-template.json). Read [references/source-operation-coverage.md](references/source-operation-coverage.md) for every compiler-path diagram or topology revision, inventory material executable operations in the selected source forward paths, and map every inventory item into the IR before layout. Source coverage and the independent topology review are mandatory for every compiler pipeline that proceeds to layout; neither may be disabled by clearing a logical-operator flag. Migrate an older IR rather than grandfathering missing records. After drafting the IR, put its node list aside, reread every pinned source path from source to sink, challenge composite/core/fused boundaries, repair omissions, and record the required independent reconciliation. Before layout, also read [references/ascii-topology-contract.md](references/ascii-topology-contract.md), declare complete `operator_sequences` for every detail region, and generate `topology.contract.txt` from the IR. Run `scripts/run_compiler_pipeline.py` for the evidence/source-coverage/topology/granularity, ASCII-review, layout, compile, and static-audit gates; pass `--audit-manifest` so machine-owned structural audit facts are generated from the same IR. Merge human-owned workflow, typography, evidence-claim, exception, and review records before strict delivery. A successful compile is a structural draft; it does not replace the existing strict delivery audit, official Draw.io rendering, or manual visual inspection.

For a cold start or any semantic topology/source revision, read [references/topology-review-workflow.md](references/topology-review-workflow.md) and run one fresh-context independent Reviewer after generating the ASCII contract but before layout. The Reviewer first records its own entrypoints, material callees, and executable operations for every selected source path, then reconciles every source-operation ID and produces a result for every required check and region. It separately proves that each ASCII region is reconstructable from named contract IDs. Finalize the completed output with `scripts/finalize_topology_review.py`; downstream gates reject a missing or stale receipt. Reuse the resulting digest-bound `topology-review.json` for geometry, typography, routing, render, or other visual-only iterations; do not invoke the Reviewer again while the canonical architecture meaning, generated ASCII, and pinned source bytes remain unchanged. A stale, placeholder, incomplete, duplicated, self-authored, unfinalized, or subsequently edited review cannot support strict delivery.

For revisions, read [references/incremental-layout.md](references/incremental-layout.md). Run change-impact analysis before layout, preserve unaffected regions, allow affected regions to adapt according to `preserve`, `adaptive`, `derived`, or explicitly requested `frozen` policies, and reapply stable-ID layout overrides. Treat incremental as controlled propagation rather than a prohibition on changing earlier content.

For exact visual refinement after global ELK, use the state override contract in [references/layout-engine-adapter.md](references/layout-engine-adapter.md). LLM-authored node/region coordinates, edge ports/waypoints and relative label positions are allowed through this validated adjustment pass, not ad hoc final XML edits. A matching previous layout avoids a new ELK run. Reconcile attached routes and regenerate hierarchy geometry; if adjustment cannot preserve valid routes, repair explicit routes or rerun layout. Compound mode rejects frozen/preserved policies rather than silently ignoring them. All ordinary strict/visual acceptance checks remain required; visual-only edits do not authorize rewriting the semantic review.

For a warm, visual-only local repair, read [references/local-revision-workflow.md](references/local-revision-workflow.md) and use `scripts/run_local_revision.py` to snapshot inputs, scope the candidate, synchronize configured focused views, and run full-master delivery/render gates. Reuse the current semantic review; do not restart source planning unless its digests changed. The command produces a review bundle, never an automatic publication or visual PASS. Its stage hints are diagnostic leads, not proven root causes.

Read [references/style-spec.md](references/style-spec.md) and [references/semantic-color-legend-contract.md](references/semantic-color-legend-contract.md) before drawing or editing. The Model Sketcher semantic palette and complete nine-entry master Legend are compiler-owned acceptance contracts, not optional polish. When the selected output includes a continuous dependency/dataflow view, also read [references/end-to-end-dataflow.md](references/end-to-end-dataflow.md).

For every hierarchy master or paired delivery, read [references/overview-level-contract.md](references/overview-level-contract.md). Treat Level 0 as a standalone model synopsis rather than a thin outer call chain: it must visibly identify the backbone, heterogeneous layer cadence/families, source-backed model-level branches, distinctive state mechanisms, and final readout that define the selected checkpoint. Level 1 then presents one complete representative composition for every materially different template family. Map every expanded Level-1 signature component back to visible Level-0 text, map every Level-1 sequence exactly once, and close every cross-level interface shape explicitly. Do not accept a generic `Decoder Stack xN` as the sole summary of several distinct attention, FFN/MoE, residual-state, or modality families.

Before choosing font sizes, node dimensions, or dependency gaps, read [references/typography-density-contract.md](references/typography-density-contract.md). Select one project-level native base size from the declared viewing profile, derive the other roles by ratio, and keep that base consistent across hierarchy levels. Do not copy a native value such as `27` into a smaller diagram merely because it worked on a large master.

Before creating or revising Level-2/Level-3 detail regions, operator/FLOPs views, or any region whose sibling nodes expose implementation steps, read [references/granularity-contract.md](references/granularity-contract.md), [references/logical-operator-contract.md](references/logical-operator-contract.md), and [references/operator-naming-contract.md](references/operator-naming-contract.md). Declare each affected region as `module-summary`, `operator-detail`, or `implementation-detail`, then classify every visible node in the entire affected region before editing. Source functions and fused kernels are execution evidence, not automatic operator-detail leaves: retain the logical tensor operators and record physical fusion separately. Reader-facing labels use paper/blog-style logical terminology; preserve exact code names in `source_symbols` instead of making readers decode them. For new diagrams or substantial detail-region revisions, enable both `require_granularity_contracts` in the project manifest and `project.require_logical_operator_contracts` in the IR; report unmigrated legacy regions as explicit debt.
Keep activation shapes on tensor edges and parameter shapes in external annotations or structured IR, not inside ordinary operator labels. A custom logical operator must state its formula and why it is atomic at the selected detail level; `Core`, `Transform`, or `Update` plus `op_type: custom` does not justify hiding a sequence.

When the evidence graph contains both model mathematics and deployment/runtime alternatives, read [references/view-projection-contract.md](references/view-projection-contract.md). Keep one complete canonical IR, classify every region/node/edge as model algorithm, inference execution, backend implementation, or shared interface, and give every entity an explicit reader-view disposition. Enable `project.require_view_projection_contracts`; the algorithm master is mandatory, while inference and backend views become mandatory when their corresponding entities exist. Never weaken source coverage to simplify a page, and never let DCP, paged-cache layout, fused kernels, or fallbacks crowd the algorithm master. Generate each requested ASCII/Draw.io projection from the same canonical IR and Reviewer digest.

For every Level-2/Level-3 expansion, implementation-detail region, or persistent cache/state object, also read [references/detail-value-runtime-state-contract.md](references/detail-value-runtime-state-contract.md). Record evidence-backed information gain for each expansion, separate materially different runtime paths such as prefill/decode into their own operator sequences, and close every persistent object's write/read lifecycle. `expanded-in-region` is only an entry mapping and never replaces direct source coverage inside the child. Cache/state objects use the compiler-owned slanted storage glyph and stay outside operator sequences; cache read/write/update operations remain ordinary operator rectangles on the applicable execution path.

Keep macro composition separate from internal block flow. Large titled regions and hierarchy children may be placed on whichever side produces the clearest ownership and shortest legal expansion corridor; use `child_direction` only for this macro arrangement. Inside every region at every level and granularity, however, ordered small blocks must use a compact vertical bottom-to-top layout without an opt-out: inputs at the bottom, outputs at the top, branches rising in parallel, and cache/state entering from the side. This includes Level 0 and Level 1 `module-summary` regions. Set `direction: column` and `flow_direction: bottom-to-top`. Use adjacent horizontal lanes only for source-backed parallel branches such as Q/K/V, experts, or alternative implementations; each lane remains vertical and a sequential chain may never be horizontal. Merely placing every successor slightly higher does not satisfy this rule: reject excessive lateral drift between adjacent sequence steps, keep shared prefixes and suffixes on a compact common trunk, and require a source-backed, reasoned exception for a genuinely distant side lane.

When the deliverable is an editable `.drawio`, when the user edits the diagram directly, or when final acceptance is requested, read [references/drawio-audit.md](references/drawio-audit.md). For a new diagram, also read [references/strict-delivery-contract.md](references/strict-delivery-contract.md) and create its evidence, topology, shape-ledger, manifest, and review records before geometry. Reuse a project-owned `*.audit.json` when present; read [references/audit-manifest-schema.md](references/audit-manifest-schema.md) when creating or changing that manifest. Run `scripts/audit_delivery_contract.py` against the final `.drawio`; do not substitute a direct permissive `audit_drawio.py` call. Then use `scripts/render_drawio.py` to export with official Draw.io and automatically run `scripts/audit_rendered_svg.py`. The renderer now fails closed when the strict project contract is absent; `--legacy-project` is only for an explicitly reported migration audit and can never support a final-pass claim. Inspect the declared full view plus detail regions after both machine checks. Rendered geometry auditing supplements manual visual inspection; it never proves aesthetic clarity. Keep model-specific cell IDs, semantics, and exceptions in the project manifest, never in the shared script.

## Workflow

Read `references/layout-engine-adapter.md`: ELK global layout is the only
compiler layout path. Do not ask the user to choose an engine or add an engine
selector to the intake table; normal commands need no engine flag. The old
native and hybrid layout paths are removed. Every ordinary edge must be ELK-owned,
including cross-region edges, before recorded precision adjustments. Inspect `elk_edge_ids` and
`native_routed_edge_ids`; never describe partial routing as full ELK coverage.
Compound output is provisional and requires the unchanged audits. Give macro
guidance through supported project-state hints, then inspect the official render;
do not assume a successful layout call means the graph is readable.

1. Select an execution mode from the request and project state: autonomous completion, checkpointed collaboration, or direct single-canvas work. Separately select one output view: hierarchy master, end-to-end dependency/dataflow master, or paired delivery. Honor an explicit choice; when starting a new diagram and the choice is absent, briefly explain the three views and ask the user to choose. Do not re-ask during a warm resume or targeted revision when the existing project or requested edit makes the view clear. Detect whether this is a cold start, a resumed project, or a targeted revision. See “Adaptive execution and evidence reuse” and “Output views” in the style specification.
2. Establish or restore the evidence base before planning topology. On a cold start, research the version-matched official report or paper, architecture figures, checkpoint/config metadata, executable model source and forward path, and relevant predecessor implementations. On a resume, load the manifest and pinned local sources first, then research only missing, stale, conflicting, or newly requested claims. Treat inference-framework code as supporting execution evidence unless it is the canonical implementation. Record every material architecture claim as code/config-confirmed, report-confirmed, inherited, inferred, conflicting, or unknown.
3. Build or update the architecture IR and shape ledger from the evidence. Set `project.require_source_coverage: true` and build the source-operation inventory before deciding what to fold: every material executable operation in each selected forward path must map to a visible node, a source-confirmed fusion, or a concrete detail expansion. A bounded selected-path view may record explicit out-of-scope or unresolved debt; a claimed complete hierarchy may not. Track inputs and outputs, projection dimensions, head counts and head dimensions, reshape/split/repeat operations, repetition scope, branches, output epilogues, runtime variants, and complete cache/recurrent-state lifecycles. Keep semantic IDs stable. Do not draw an inferred operation as an established code path. After the draft, perform the independent source-first reread required by the coverage contract; do not validate the IR only against its own inventory. Recursively inventory every expanded child; an umbrella `expanded-in-region` record is not child coverage.
4. Plan the complete architecture: model overview, repeated block, layer templates, operator implementations, shared call-sites, and side branches. Before geometry for a hierarchy master, read [references/hierarchy-layout.md](references/hierarchy-layout.md), then create both (a) a strict containment/ownership tree and (b) a separate typed call-and-reuse DAG. Every containment node has exactly one parent; a shared implementation is defined once and referenced by its callers rather than duplicated under multiple templates. Record each planned expansion as `actual parent definition → child detail`, including items deliberately left unexpanded. Record calls, injections, and reuse separately; a call-site is not an expansion parent unless it also owns the definition. Keep that semantic parent stable, but choose the physical expansion representation independently: attach directly to the parent node when the corridor is clean, use a named `owner-region-boundary` egress when the enclosing region owns the parent and direct attachment would crowd local flow, or let the layout planner use a labeled target-side signpost only after all four direct placements are exhausted. A signpost remains registered to the real parent and points into the exact child boundary; it is not a second parent or an unregistered floating decoration. Before assigning coordinates, group model-level siblings together and reserve a distinct external expansion corridor; do not enlarge execution content to hold it. Do not anchor the backbone to a conventional corner or force all children into one row: move the backbone, put auxiliary heads above it, place modality/embedding branches beside it, and enlarge or change the canvas aspect ratio when that produces clearer ownership. A hierarchy expansion may use a straight hollow block arrow or a wide hollow orthogonal arrow with bends; choose the shortest unambiguous representation from the registered semantic parent to the exact child boundary. A lower implementation band is allowed only when every child has an unambiguous labeled expansion source and its placement cannot visually nest it beneath or align it as the continuation of an unrelated module. For an end-to-end view, record producer/consumer dependencies, the continuous input-to-output tensor spine, shared implementation reuse, and legal repetition folds. For paired delivery, derive both views from the same contracts and ledger. See “Hierarchy plan and master canvas” and the end-to-end reference.
   For every detailed leaf module, create a branch ledger containing source, parameterized operation, output shape, post-processing, and consumer. Draw separate lanes whenever branches use independent parameters, produce different shapes, receive different normalization/cache/reshape treatment, or feed different consumers. In an `operator-detail` region, one ordinary box is one logical tensor operation or one zero-arithmetic view transformation. Show a packed projection once, then an explicit split and separate output lanes. Preserve the logical nodes inside an implementation fusion and record their membership in `execution_fusions`; only `implementation-detail` may use one fused-kernel node as the execution leaf. An `operator-detail` composite marked `expanded-elsewhere` must expand into another `operator-detail`; a Level-3 runtime/kernel region cannot stand in for the missing logical sequence.
5. Encode the topology in `architecture.json`, then generate the compact ASCII topology contract for review; never maintain an independently edited duplicate. Record the layout axis and flow direction, ordered modules, repetition boundary and count, tensor shapes, branch source and destination, expansion targets, detail information deltas, runtime variants, and state lifecycles. Keep each contract focused on one main level; split mixed model-level and layer-internal logic into separate contracts. Every region containing two or more semantic small blocks must expose complete named `operator_sequences` before geometry, including Level 0/1 module summaries. Each sequence is a vertical bottom-to-top lane; multiple sequences may sit side by side only when the source proves real parallelism. Level-2/Level-3 detail regions always require complete sequences. Persistent cache/state nodes are side-lane storage and never sequence members. An ordinary RMSNorm, projection, activation, reshape, cache update, or reduction is one node. A source-level fused call does not waive this operator-detail rule; represent fusion separately. Give every logical leaf an `op_type`, `semantic_role`, and exact `source_symbols`; make its first-line label reader-facing rather than a raw code identifier. Resolve every non-junction node to the canonical Model Sketcher semantic palette and glyph, using `visual_class` where the deterministic default would lose meaning and `visual_modifiers: [tp-partition]` for TP-specific red text. Complete `operator_naming_review` across every operator-detail region. Run the logical-operator, naming, semantic-color/glyph, structured tensor-shape, semantic IR, and ASCII gates, then obtain a digest-bound independent topology review before assigning geometry. Re-run that Reviewer only after a semantic/source change, not after layout-only work.
6. Declare the intended viewing profile before final geometry. Include both the whole-master overview and the primary reading frame: the model backbone, a focused level, or another region expected to fill one ordinary screen. Size text from its apparent on-screen result, not from inherited draw.io defaults. In the reference-calibrated Model Sketcher profile, a one-line block label should be effortless to read in the primary frame (roughly 16–18 px apparent), while hierarchy-arrow and relationship labels remain clearly readable but subordinate (roughly 12–14 px apparent). At about 0.6 fit scale, native draw.io/SVG values near 27 for block labels and 20 for hierarchy-arrow labels are a useful starting calibration, not universal constants. Define role-based node padding and dependency-aware gaps before geometry, then adjust them consistently rather than sizing each block ad hoc. Size ordinary nodes to their content; keep routing lanes, alignment grids, and branch corridors independent from visible node width. See “Presentation scale, typography, and collision budget” in the style specification.
   Record the selected values in a project `typography_contract`. A hierarchy level never changes the ordinary-node font by itself: Level 0 and Level 3 use the same ordinary-node base unless their semantic roles differ. Compute compact node widths from rendered text plus role padding; a wider port-bearing or alignment box needs a recorded exception. Compute vertical gaps from edge-label height and routing needs rather than a fixed loose grid.
7. Confirm the evidence, selected output view, architecture plan, contracts, and symbol sketch together. Represent fixed layer layouts with separate blocks and `×N`; never turn them into runtime `if` diamonds. In a hierarchy master, do not mix more than two adjacent levels in one bounded subgraph. In an end-to-end master, integrate levels by dependency rather than by hierarchy arrows and fold only structurally identical repetition.
8. Choose the lightest suitable drawing structure. A small focused legacy edit may be drawn directly on one canvas. For compiler-path work, generate deterministic geometry first, then refine explicit, recorded layout exceptions rather than hand-editing compiled XML. Keep every port finite, normalized, boundary-attached, and manifest-bound. Put any necessary edge-label displacement in the validated layout `label_position`, never in a compiled-XML polish pass. For a multi-level final diagram, use a master-first/focused-detail workflow: validate complex modules on focused pages, then integrate each stable module back into the master incrementally instead of postponing all composition until the end.
   If a strict audit produces a large pairwise failure set, read [references/layout-failure-recovery.md](references/layout-failure-recovery.md) before changing coordinates. Cluster findings by region, implicated edge, and shared corridor; rebuild a structurally failed focused region instead of chasing individual edge pairs. Use one early low-scale official diagnostic export to reject a bad macro composition, but do not repeat full-resolution official exports or claim visual acceptance while static errors remain.
   In a hierarchy compiler project, encode every parent-to-child expansion as `kind: expand`. It must compile to a large white hollow block-arrow vertex and a generated `hierarchy_anchors` entry, never to an ordinary edge with a small arrowhead. `source` remains the semantic parent; optional IR `visual_attachment` may select that node or an owning region boundary plus a visible `anchor_label` and preferred side. Lay out compact execution content first; hierarchy-arrow corridors are external relationship geometry and may not widen ordinary nodes, spread parallel lanes, inflate owner regions, or create internal dead space. Evaluate north, south, east, and west child placement before committing macro coordinates; do not assign one direction to every expansion merely to form level bands. When direct attachment would distort the execution graph, use a named owner-region egress; use a separate canonical-definition node only when that shared definition is source-backed, never as a layout-only proxy. If all four direct parent/egress corridors remain illegal because several large children compete for the same owner, the planner may derive `target-signpost` in `layout.json`: a compact labeled block arrow immediately outside and pointing into the child, with manifest ownership still bound to the real source and owner region. `target-signpost` is generated fallback geometry, not an architecture-IR option, and explicit `parent-node` may never be promoted to it. A straight block arrow whose length-to-thickness ratio exceeds the shared limit is cable-like and blocks delivery unless a source-backed obstacle requires a narrow reviewed exception; normally move the child to a nearer side or use a compact bent block arrow. After any project-specific node or region reflow, regenerate hierarchy-arrow geometry from the final boxes before compilation. If the centered shaft covers actual content, first choose a legal owner-region egress or use a project-state hierarchy-arrow corridor override; neither mechanism may change semantic ownership or bypass geometry, label, ownership, compactness, or obstacle audits. Missing, stale, undersized, detached, obstructing, ambiguous, falsely owned, overlong, or unregistered expansion arrows block delivery.
9. Keep focused pages and the master synchronized from one topology source of truth. Reuse structured module definitions when tooling supports it; otherwise reconcile both against the same contracts before every integration. Never maintain two independently evolving architectures.
10. Within each detailed subgraph, use black orthogonal tensor-flow arrows and label shape changes on the edges. Separate materially different paths—such as training/inference, prefill/decode, or alternative fixed layer templates—into individually titled dashed blocks.
   Prefer a non-crossing route. When one isolated perpendicular crossing remains after port exchange, lane reordering, and local reflow, declare a layout `line_jump` so one edge renders a small audited arc bridge over the other. A legacy crossing allowlist or an unbridged intersection is not acceptable. Line jumps express non-connection; they may not excuse a dense routing wall, a T-intersection, a crossing near a bend/endpoint/label, or any positive-length collinear overlap. Collinear sharing remains legal only for a declared directionally clear semantic rail or bus.
   Before geometry, make a node-semantic ledger: every rectangular, operator, cache, and interface symbol must map to a source-backed module, operation, persistent artifact, or explicitly declared model boundary. Treat modules and operators as nodes, while transient tensors normally remain edge labels. Keep a tensor as a node only when it is a model/subgraph interface, persistent cache or recurrent state, repetition boundary, necessary multi-consumer checkpoint, or independently meaningful stored artifact. A routing-only merge, split, or fan-out is a small visible junction or edge label—not a colored module box, IO box, or pseudo-dispatch node. Do not turn names such as `Rin`, `Rmid`, `Rout`, or `x` into ordinary rectangular nodes merely to make routing easier.
   Treat clearance as geometry, not merely as absence of intersection. Sibling operators in one immediate owner region need a visible scale-derived gutter. A side route must retain clear air while running parallel to its own endpoint box, every unrelated node, and its owner-region boundary; a mathematically positive gap of only a few pixels is still a blocking visual collision. Use the compiler-generated clearance thresholds and narrow reasoned pair exceptions from the audit manifest rather than model-specific IDs in shared code.
11. For every compiler-path project, preserve `architecture.json`, generated `topology.contract.txt`, `layout.json`, `project-state.json`, and the delivery manifest alongside the evidence and shape files. `project-state.json` records the last successful gate, accepted and blocked regions, unresolved claims, and last audit. These project files—not chat history or model memory—are the recovery point for a new session.
12. When parallel work is useful and available, follow “Optional multi-agent execution” in the style specification. Keep one topology owner and one master composer; parallelize evidence extraction and independent review rather than uncoordinated final layouts.
13. Treat editable `.drawio` as the canonical visual artifact whenever Draw.io is the user's editing target. Serialize declared edge endpoints as explicit Draw.io entry/exit ports rather than relying on editor auto-routing. For every new project, pass the strict delivery-contract audit before official rendering; a permissive manifest or successful export is not an acceptance state. Enable the generic density preflight for new compiler-path projects so sparse region content, large internal whitespace pockets, trailing whitespace, large adjacent-region gaps, font-role drift, and undersized apparent text enter the review queue before manual inspection. Export the final PNG/SVG from diagrams.net/Draw.io itself; run the rendered-SVG geometry auditor on that official SVG, then inspect the exports. Treat `FAIL` as blocking, `WARN` as a targeted manual-review queue, and never relabel either as a visual pass without inspection. Do not copy or promote preview artifacts after any failed gate. A separately implemented SVG renderer may be used only as a quick preview; if a Draw.io renderer is unavailable, report the result as structurally audited but not visually accepted. Export an editable `.drawio` and a `.png` preview unless the user explicitly requests other formats.
14. Treat an edge label that touches an arrowhead or hides a route bend as a blocking rendered defect. Check the official route against its own source and target interiors, because Draw.io auto-routing can create a hook that re-enters an endpoint even when XML waypoints look legal. For every fan-out with three or more consumers, declare whether the common tensor shape belongs on the source/interface node or must be repeated on every branch; never attach a shared shape to only one sibling branch.
15. Treat route simplicity as both a pre-render and rendered-geometry gate. An explicit route must leave and approach a rectangular endpoint normal to its selected side: east/west ports begin/end horizontally and north/south ports vertically. Reject visible backward hooks and unnecessary alternating-axis doglegs between nearly aligned one-in/one-out execution endpoints. Also reject a monotonic multi-bend staircase when an endpoint-direction-compatible L-route removes at least two bends without increasing length or crossing a real obstacle; near-axis checks alone do not cover this case. Downgrade subpixel reversals, invisible collinear metadata, and doglegs with a detected direct-corridor obstacle to targeted review. Do not infer relation semantics from line width alone: the standard hierarchy/reuse relation is thick and hollow, while a thick filled tensor remains execution flow. Fix alignment or ports in the layout source instead of cosmetically editing compiled XML; permit a narrow route-quality exception only when a named obstacle or lane contract requires the bend.

## Non-negotiable review

Before delivery, inspect both the full-canvas preview at the declared target viewport and at least two detailed crops at their declared detail scale. Reject and revise the diagram if any of these are true:

- operator nodes look like large rounded cards or presentation tiles;
- an untitled dashed boundary leaves ownership ambiguous;
- prose cards, training notes, or lineage notes sit inside an execution subgraph;
- fixed topology is represented as a flowchart decision;
- tensor shapes are mostly inside nodes instead of adjacent to their edges;
- transient intermediate tensors are rendered as module-like boxes without an interface, persistence, repetition, or fan-out reason;
- any visible rectangular/operator/interface node lacks a source-backed semantic-ledger entry, or a layout-only junction is styled or labeled as a real module, tensor interface, or execution dispatch;
- a binary operator changes rank or produces an output shape that does not close dimensionally, without an explicit reshape, unsqueeze, broadcast, reduction, concatenate, or outer-product annotation;
- distinct branches overlap or share routes that make direction unclear;
- unrelated tensor edges cross without an explicit semantic junction, or share a collinear segment without a declared same-direction fan-out rail;
- an edge takes an avoidable long detour or extra bends when exchanging source/target ports, reordering sibling lanes, or shifting a local node would produce a shorter non-crossing route;
- two visible nodes overlap without an explicit containment semantic, even when both labels individually fit;
- an incoming edge and an outgoing edge use the same node port and collinear segment, or opposite directions share a segment without an explicit junction, making arrow direction ambiguous;
- an explicitly routed edge starts or ends away from its declared source/target boundary, or any of its segments passes through an unrelated visible node;
- Draw.io is the editing target but explicit source/target ports were omitted, allowing diagrams.net to replace a declared route with center-to-center auto-routing;
- visual acceptance was based only on an independently rendered SVG/PNG instead of a diagrams.net/Draw.io export; when that renderer is unavailable, the delivery must say that Draw.io visual acceptance remains pending;
- hierarchy arrows are absent or tiny in a hierarchy master, or are confused with tensor arrows in any view;
- an `expand` arrow is absent from the hierarchy-anchor registry, names no concrete semantic parent and child identifiers, floats in unregistered whitespace, or fails either its registered parent/owner attachment plus child-boundary checks or its audited target-signpost child-boundary, direction, ownership-label, and obstacle checks;
- a straight hierarchy arrow is used only because the drawing implementation lacks bendable arrows, forcing child placement, obscuring the exact source/target, or producing a less clear layout than a wide hollow orthogonal route;
- a child detail region is spatially nested under, aligned as the apparent continuation of, or reached by the expansion corridor of a module that is not its actual expansion parent;
